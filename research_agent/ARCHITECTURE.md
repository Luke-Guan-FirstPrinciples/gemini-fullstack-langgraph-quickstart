# Research Agent — Architecture & FAQ

## Architecture Overview

The research agent is a **LangGraph-based pipeline** that takes a natural language research query and produces structured academic output (papers, labs, fields, keywords) via LLM-powered search, enrichment, and ranking.

### Pipeline (4 core nodes, iterative loop)

```
parse_query → execute_search → structure_results → assess_coverage
                 ↑                                      │
                 └──────── (sub-queries if gaps) ───────┘
```

After the core loop, post-processing steps enrich and rank the results.

### File Map

| File | Purpose |
|------|---------|
| `graph.py` | LangGraph pipeline definition — nodes, edges, state |
| `models.py` | Pydantic schemas (`ResearchState`, `Paper`, `Lab`, etc.) |
| `prompts.py` | System/human prompts for each LLM node |
| `llm.py` | LLM factory — Gemini (default), OpenAI, or Anthropic |
| `search/` | Pluggable search providers (Google CSE, Tavily, Jina, OpenAI) |
| `search/base.py` | Abstract `SearchProvider` interface |
| `search/factory.py` | Instantiates the configured search provider |
| `enrichment.py` | Post-search enrichment via academic APIs (OpenAlex) |
| `ranking.py` | Multi-signal paper reranking (semantic + bibliometric) |
| `config.py` | Environment-variable-based settings |
| `cli.py` | CLI entry point (`python -m research_agent "query"`) |
| `app.py` | FastAPI application |
| `logging_config.py` | Dual-handler logging (console + file) |

## Node-by-Node Breakdown

### 1. `parse_query`

Decomposes the user's natural language query into 4–6 targeted search queries.

- **Input:** user query string
- **Output:** `ParsedQuery` — intent, fields, key_terms, date_constraint, search_queries
- **How:** Single LLM call with structured output. The prompt in `prompts.py` instructs the LLM to generate queries with `site:` operators targeting academic sources (arxiv.org, nature.com, journals.aps.org, etc.).

> **Key point:** The `site:` operators in search queries are generated by the LLM in this step, not by the search provider. The search provider simply forwards the query strings as-is.

### 2. `execute_search`

Runs all search queries in parallel through the configured search provider.

- **Input:** list of search query strings from `parse_query`
- **Output:** raw `SearchResult` objects (title, url, snippet, source)
- **How:** Async parallel execution via the `SearchProvider` abstraction. No LLM calls — pure API calls to the search backend.
- **Deduplication:** repeated raw search hits are filtered by canonical URL and title/source keys before they are appended into `all_search_results`.

#### Available search providers

| Provider | API | Credentials |
|----------|-----|-------------|
| Google CSE | Google Custom Search JSON API v1 | `GOOGLE_CSE_API_KEY`, `GOOGLE_CSE_ID` |
| Tavily | Tavily REST API | `TAVILY_API_KEY` |
| Jina | Jina AI Search API | `JINA_API_KEY` |
| OpenAI | OpenAI Responses API with `web_search_preview` | `OPENAI_API_KEY` |

### 3. `structure_results`

Parses raw search results into structured academic objects.

- **Input:** all accumulated search results + original query
- **Output:** `ResearchOutput` — papers, labs, fields, keywords, sub_queries
- **How:** **One LLM call** for all results. Builds a single text block of all results (title, URL, snippet) and sends it to the LLM, which returns the full structured output in one response. It does **not** make one call per paper.

### 4. `assess_coverage`

Evaluates whether the results sufficiently cover the query.

- **Input:** structured output + original query + iteration count
- **Output:** `CoverageAssessment` — is_sufficient, gaps, sub_queries
- **How:** Prompt-based. A single LLM call evaluates three things:
  1. Is coverage **sufficient** — are the major aspects of the query represented?
  2. If not, what are the **specific gaps** (missing sub-topics, time periods, source types)?
  3. For each gap, a **targeted search query** with `site:` operators to fill it.
- **Loop control:** If `is_sufficient` is false and iterations remain, the sub_queries feed back into `execute_search`. Otherwise the pipeline terminates.
- **Truncation:** Structured results are truncated to 8,000 characters to avoid token limits.

## Post-Processing: Enrichment & Ranking

### Enrichment (`enrichment.py`)

After the core graph loop, papers are enriched with metadata from academic APIs (OpenAlex and Semantic Scholar). This provides structured data that web search cannot: citation counts, canonical paper IDs, publication venues, and other bibliometric signals.

After enrichment, duplicate paper records are merged using DOI, OpenAlex IDs, Semantic Scholar IDs, and canonicalized title/year fallbacks before reranking.

### Ranking (`ranking.py`)

Papers are scored and ranked using two signals:

| Signal | Source | Normalization |
|--------|--------|---------------|
| `semantic_relevance` | LLM reranking call | LLM scores each paper's relevance to the query (0–1). Falls back to token overlap if the LLM call fails. |
| `citation_count` | Semantic Scholar enrichment | `log1p(citation_count)` divided by the max across all papers in the run. Most-cited paper ≈ 1.0. |

The final **score** is a weighted sum of both signals. Weights are configurable via `cfg.ranking_weights()` and normalized to sum to 1.0.

## State Management

The LangGraph state (`ResearchState` in `models.py`) tracks everything across iterations:

```python
class ResearchState(TypedDict):
    query: str
    parsed_query: dict | None
    search_queries: list[str]
    all_search_results: Annotated[list[dict], add]  # accumulates across loops
    structured_output: dict | None
    iteration: int
    max_iterations: int
```

The `all_search_results` field uses LangGraph's `Annotated[list, add]` reducer. `execute_search` returns only new unique results for each loop, so the accumulated list stays deduplicated while `structure_results` still processes the full set.

## LLM vs Search Provider Independence

The LLM provider and search provider are **configured independently**:

- `--llm-provider` controls which LLM handles `parse_query`, `structure_results`, `assess_coverage`, and reranking
- `--search-provider` controls which API executes the web searches in `execute_search`

This means you can mix providers, e.g. Gemini for LLM reasoning + OpenAI for web search. Both are set via CLI flags or environment variables in `config.py`.

---

## Why `execute_search` and `structure_results` Are Separate Nodes

These two nodes are intentionally not merged:

1. **Accumulation logic** — `execute_search` appends new results via the `add` reducer. `structure_results` re-processes the entire accumulated list. Merging would require managing accumulation manually inside one function.
2. **Debuggability** — LangSmith/logs show raw search results as a distinct step, making it easy to tell whether a bad output is a search problem or an LLM structuring problem.
3. **Retry granularity** — if the LLM structuring call fails (token limit, rate limit), the searches don't need to re-run.
4. **Swappability** — the search node and structuring prompt can evolve independently.

---

## Search Strategy: Web Search vs Academic APIs

The current architecture uses **web search** (general search APIs with `site:` operators). Academic APIs like Semantic Scholar and arxiv have structured metadata but **don't work well with natural language** — they require keyword-based or ID-based queries.

A hybrid approach would be:

1. **Web search** to discover papers (current approach)
2. **Academic API enrichment** after discovery — look up papers by DOI or title in Semantic Scholar/OpenAlex to get structured metadata (citations, abstracts, canonical paper metadata)

This is the approach used today: web search for discovery, then OpenAlex plus Semantic Scholar for enrichment. It avoids the query translation problem while still getting structured academic data.

## Observability

### Logging

Dual-handler setup in `logging_config.py`:
- **Console:** INFO level to stderr
- **File:** DEBUG level to `logs/research_agent/run_YYYYMMDD_HHMMSS.log`

Results are saved to `logs/research_agent/results_YYYYMMDD_HHMMSS.json`.

### LangSmith Tracing

Not enabled by default. To enable, set these environment variables:

```bash
export LANGCHAIN_TRACING_V2=true
export LANGCHAIN_API_KEY=your-langsmith-api-key
export LANGCHAIN_PROJECT=research-agent
```

No code changes required — LangChain/LangGraph automatically sends traces to LangSmith. Each node appears as a separate span with inputs, outputs, and token usage visible at [smith.langchain.com](https://smith.langchain.com).
